# Инструкции для Codex в проекте Zorix

Статус документа: черновик.

Этот документ описывает, как Codex должен работать с репозиторием Zorix. Он предназначен для задач по документации, структуре проекта и будущим инженерным изменениям.

На текущем этапе Zorix не требует написания кода без отдельного явного запроса.

## Базовый контекст

Zorix — будущая open-source платформа для безопасного взаимодействия AI с реальной инфраструктурой.

Проект ориентирован на русскоязычную аудиторию и находится на раннем этапе формирования основания.

Codex должен учитывать, что:

- Zorix не является просто MCP-сервером;
- Zorix не является просто DevOps Toolkit;
- Zorix не является автономным AI-оператором production-инфраструктуры;
- Zorix должен развиваться как фундамент для AI-native Infrastructure Intelligence Platform;
- документы не должны обещать функциональность, которой еще нет.

## Перед началом задачи

Перед внесением изменений Codex должен:

- проверить текущее состояние репозитория;
- прочитать релевантные файлы;
- определить, какие файлы относятся к задаче;
- не трогать несвязанные изменения;
- уточнить задачу, если без уточнения можно легко расширить scope.

Если пользователь прямо запрещает писать код, Codex не должен создавать техническую реализацию, даже если это кажется естественным следующим шагом.

## Стиль работы с документацией

Документы должны быть на русском языке, если пользователь не указал иное.

Предпочтительный стиль:

- спокойный;
- точный;
- инженерный;
- без маркетинговых лозунгов;
- без преувеличений;
- без обещаний нереализованной функциональности.

Не следует использовать формулировки, которые создают впечатление готового продукта, если проект находится на концептуальном этапе.

## Что нельзя делать без явного запроса

Codex не должен:

- писать код;
- создавать техническую реализацию;
- добавлять зависимости;
- менять структуру проекта шире поставленной задачи;
- переименовывать файлы без необходимости;
- удалять существующие материалы;
- исправлять несвязанные документы по собственной инициативе;
- добавлять функции в описание проекта, если они не были согласованы.

## Как описывать будущие возможности

Если в документе нужно упомянуть будущую возможность, ее следует описывать осторожно:

- как направление;
- как предполагаемую область развития;
- как архитектурную тему;
- как вопрос для будущего проектирования.

Не следует писать так, будто возможность уже доступна пользователю.

## Review перед ответом пользователю

Перед финальным ответом Codex должен проверить:

- изменены только запрошенные файлы;
- документы написаны на русском языке;
- нет кода, если задача была документальной;
- нет маркетинговых формулировок;
- нет обещаний несуществующей функциональности;
- не затронуты чужие или несвязанные изменения;
- результат можно кратко и честно описать пользователю.

## Тон ответа

Финальный ответ должен быть кратким и по делу.

Нужно указать, какие файлы были заполнены, и отдельно отметить, что другие файлы проекта не изменялись, если это соответствует фактическому результату.
