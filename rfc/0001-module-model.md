# RFC 0001: Модульная модель Zorix

Статус: принято.

## 1. Назначение документа

Этот документ фиксирует принятую модульную модель Zorix.

RFC описывает, как проект должен мыслить границы модулей, их ответственность и правила взаимодействия между ними. Документ не описывает готовую реализацию, не вводит API и не является технической спецификацией отдельных компонентов.

Цель RFC — задать архитектурную основу, которая поможет проекту развиваться без смешивания разных уровней ответственности: интерфейсов, инфраструктурных интеграций, политик, контекста, исполнения и аудита.

## 2. Проблема

Zorix должен развиваться как основа для AI-native Infrastructure Intelligence Platform, а не как один инструмент, один протокол или один набор команд.

Без явной модульной модели проект быстро столкнется с несколькими проблемами:

- интеграции начнут определять архитектуру ядра;
- интерфейсы будут смешиваться с бизнес-логикой платформы;
- чтение инфраструктурного контекста может оказаться неотделимым от изменения состояния;
- правила безопасности и аудита будут добавляться после появления действий, а не до них;
- разные части проекта начнут делать предположения о правах, рисках и ответственности друг друга;
- будущим участникам будет сложно понять, где заканчивается один слой системы и начинается другой.

Для Zorix это особенно важно, потому что проект работает с областью, где ошибка архитектурной границы может привести к опасной модели доступа.

AI не должен получать возможность взаимодействовать с инфраструктурой через неявный набор прав и скрытых связей между компонентами. Любой будущий механизм должен иметь понятную область ответственности, явные ограничения и проверяемое поведение.

## 3. Принятое решение

Zorix принимает модульную модель как базовый архитектурный принцип.

Модуль в Zorix — это самостоятельная область ответственности внутри платформы, имеющая понятное назначение, границы, входные данные, выходные данные и ограничения.

Модуль не должен существовать только как техническая папка в репозитории. Модуль должен отражать устойчивую архитектурную роль.

Принятая модель предполагает, что Zorix будет развиваться через разделение следующих типов ответственности:

- работа с инфраструктурным контекстом;
- описание и применение политик;
- классификация и подготовка действий;
- взаимодействие с внешними инфраструктурными системами;
- пользовательские и машинные интерфейсы;
- аудит, журналирование и трассировка;
- контроль рискованных операций;
- хранение и передача проектных контрактов.

Эти области не означают, что все соответствующие модули уже существуют или должны быть реализованы одновременно. RFC фиксирует принцип разделения, а не план немедленной реализации.

Ключевое решение: никакой отдельный интерфейс или интеграция не должен определять всю архитектуру Zorix.

MCP, CLI, API, Kubernetes-интеграции, Terraform-интеграции или другие будущие механизмы должны рассматриваться как части платформенной модели, а не как ее центр.

## 4. Правила для модулей

Каждый модуль должен иметь явно описанное назначение.

Если назначение модуля нельзя объяснить без перечисления случайного набора функций, модуль считается архитектурно незрелым.

Каждый модуль должен иметь ограниченную область ответственности.

Модуль не должен одновременно отвечать за получение контекста, принятие решения, выполнение действия и аудит результата. Такие роли должны разделяться, если они имеют разные риски и разные требования к проверке.

Каждый модуль должен различать чтение, анализ и изменение состояния.

Операции чтения инфраструктурного контекста не должны автоматически давать право изменять инфраструктуру. Анализ не должен неявно превращаться в выполнение. Подготовка действия не должна считаться подтверждением действия.

Каждый модуль должен быть проектируем с учетом безопасности.

Модуль не должен предполагать неограниченное доверие к AI-выводу, внешнему инструменту или соседнему компоненту. Права, границы и риск должны быть явными.

Каждый модуль должен оставлять возможность проверки.

Для значимых операций должно быть понятно, какие входные данные использовались, какой результат был получен, какие ограничения применялись и как это можно проверить.

Каждый модуль должен иметь документированные контракты.

Если модуль принимает или возвращает данные, влияет на политику, формирует действие или взаимодействует с внешней системой, его поведение должно быть описано достаточно ясно для review и дальнейшей поддержки.

Каждый модуль должен быть заменяемым в пределах своей роли.

Архитектура не должна строиться так, чтобы один конкретный провайдер, протокол, runtime или инфраструктурный инструмент становился неявной основой всего проекта.

Каждый модуль должен быть честно описан с точки зрения зрелости.

Экспериментальный модуль не должен выглядеть как стабильный контракт. Концептуальный модуль не должен описываться как готовая функциональность.

## 5. Ограничения

Модульная модель не означает немедленное создание большого количества компонентов.

На раннем этапе Zorix должен сохранять простоту и не добавлять модули без ясной архитектурной причины.

Модульная модель не должна использоваться как оправдание преждевременной абстракции.

Если область ответственности еще не подтверждена проектными документами, практическими сценариями или архитектурной необходимостью, ее не следует выделять в самостоятельный модуль только ради симметрии.

Модульная модель не отменяет необходимость единого ядра проекта.

Даже при разделении ответственности Zorix должен сохранять согласованную модель безопасности, терминологию, правила аудита и понимание инфраструктурного риска.

Модульная модель не должна скрывать опасные действия за нейтральными интерфейсами.

Если модуль может привести к изменению состояния инфраструктуры, это должно быть явно отражено в его назначении, ограничениях и будущих контрактах.

Модульная модель не должна превращать Zorix в набор несвязанных интеграций.

Интеграции важны, но они должны подчиняться платформенной модели, а не заменять ее.

## 6. Возможные будущие модули

Ниже перечислены возможные будущие модули как архитектурные направления. Этот список не является планом реализации и не означает, что перечисленные модули уже существуют.

Модуль контекста может отвечать за получение, нормализацию и передачу инфраструктурного контекста без права самостоятельно изменять состояние систем.

Модуль политик может отвечать за описание и проверку правил доступа, ограничений и условий выполнения действий.

Модуль действий может отвечать за представление потенциальных операций как структурированных намерений с уровнем риска, областью применения и ожидаемым эффектом.

Модуль подтверждений может отвечать за контроль рискованных операций, требующих участия человека или внешнего процесса approval.

Модуль аудита может отвечать за фиксацию значимых событий, решений, проверок, запросов и результатов.

Модуль интеграций может отвечать за взаимодействие с внешними инфраструктурными системами, не смешивая это взаимодействие с политиками и принятием решений.

Модуль интерфейсов может отвечать за способы взаимодействия с Zorix, включая будущие CLI, API, MCP или другие интерфейсы, не превращая любой из них в центр архитектуры.

Модуль контрактов может отвечать за схемы, форматы данных и стабильные соглашения между частями платформы.

Модуль наблюдаемости может отвечать за техническую видимость работы системы: метрики, события, трассировку и диагностический контекст.

Каждый из этих модулей должен появляться только тогда, когда его назначение, границы и риски достаточно понятны. Для Zorix важнее сохранить ясную архитектурную модель, чем быстро увеличить количество компонентов.
