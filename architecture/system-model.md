# Системная модель Zorix

Статус: принято.

## 1. Назначение документа

Этот документ фиксирует базовую системную модель Zorix.

Модель определяет пять сущностей, через которые описывается взаимодействие Zorix с инфраструктурой: `Workflow`, `Tool`, `Resource`, `Adapter` и `Event`.

Документ не вводит новые сущности, не описывает техническую реализацию и не является спецификацией API. Его задача — зафиксировать общий язык для будущей архитектуры, документации и review решений.

## 2. Пять базовых сущностей

В Zorix существует пять базовых сущностей.

### Resource

`Resource` отвечает на вопрос: что существует?

Это описание инфраструктурного объекта или логической единицы, с которой может работать Zorix.

Примеры ресурсов:

- `Server`;
- `Service`;
- `Container`;
- `Database`;
- `Volume`;
- `Repository`;
- `Certificate`;
- `Network`.

`Resource` не содержит действий и не принимает решений. Он описывает объект, но не определяет, что с ним можно делать.

### Tool

`Tool` отвечает на вопрос: что можно сделать?

Это операция или возможность, применимая к `Resource`.

Примеры инструментов:

- `Inspect`;
- `Restart`;
- `Backup`;
- `Create`;
- `Update`;
- `Delete`.

`Tool` всегда работает с `Resource`. Он не должен обращаться к инфраструктуре напрямую и не должен обходить `Adapter`.

### Adapter

`Adapter` отвечает на вопрос: как связаться с реальным миром?

Это слой взаимодействия с конкретной платформой, системой или внешней средой.

Примеры адаптеров:

- `Linux Adapter`;
- `Docker Adapter`;
- `SSH Adapter`;
- `GitHub Adapter`;
- `Cloudflare Adapter`.

`Adapter` знает особенности конкретной платформы, но не принимает архитектурных решений. Его задача — выполнять связку между моделью Zorix и внешней инфраструктурой в рамках полученного действия.

### Workflow

`Workflow` объединяет несколько `Tool` в единый сценарий.

Он описывает последовательность действий, но не должен напрямую обращаться к `Resource`, `Adapter` или инфраструктуре в обход `Tool`.

`Workflow` нужен для сценариев, где одиночного действия недостаточно: например, когда перед изменением состояния нужно выполнить проверку, затем действие, затем проверку результата.

### Event

`Event` фиксирует факт, произошедший в системе.

Примеры событий:

- `ContainerStarted`;
- `DeploymentFailed`;
- `CertificateExpired`.

`Event` должен отражать значимые изменения, результаты действий и состояния, которые важны для аудита, истории и последующего анализа.

## 3. Связи между ними

`Workflow` использует `Tool`.

`Tool` работает с `Resource`.

`Tool` обращается к инфраструктуре только через `Adapter`.

`Adapter` взаимодействует с внешней инфраструктурой и возвращает результат в модель Zorix.

`Event` фиксирует значимый факт, связанный с выполнением действия, изменением состояния или результатом проверки.

Инфраструктура находится за пределами пяти базовых сущностей. В этой модели она рассматривается как внешняя среда, доступ к которой должен проходить через `Adapter`.

Базовая цепочка взаимодействия выглядит так:

1. `Workflow` определяет сценарий.
2. `Workflow` вызывает один или несколько `Tool`.
3. `Tool` применяется к конкретному `Resource`.
4. `Tool` использует `Adapter` для связи с внешней инфраструктурой.
5. Результат значимого действия или наблюдения фиксируется как `Event`.

## 4. Основные правила

1. В системной модели Zorix существует только пять базовых сущностей: `Workflow`, `Tool`, `Resource`, `Adapter`, `Event`.
2. `Resource` описывает объект и не содержит действий.
3. `Tool` описывает действие и всегда работает с `Resource`.
4. `Tool` никогда не обращается напрямую к инфраструктуре.
5. `Tool` всегда работает через `Adapter`.
6. `Adapter` знает особенности конкретной платформы, но не принимает архитектурных решений.
7. `Workflow` использует только `Tool`.
8. `Workflow` не должен обходить `Tool` и напрямую работать с `Adapter`.
9. Любое значимое действие должно приводить к появлению `Event`.
10. `Event` фиксирует факт, а не принимает решение.
11. Чтение состояния, изменение состояния и фиксация факта должны оставаться различимыми.
12. Ни одна из сущностей не должна скрывать риск инфраструктурного действия.

## 5. Пример взаимодействия

Пример: проверка и перезапуск контейнера.

В модели Zorix такой сценарий описывается через пять базовых сущностей:

1. `Resource` описывает контейнер, с которым нужно работать.
2. `Workflow` задает сценарий: проверить состояние контейнера, выполнить перезапуск при необходимости, проверить результат.
3. `Workflow` вызывает `Tool` для проверки состояния.
4. `Tool` применяет действие к `Resource` и обращается к инфраструктуре через `Adapter`.
5. `Adapter` выполняет связь с конкретной платформой, например Docker.
6. После проверки состояния создается `Event`, фиксирующий результат наблюдения.
7. Если сценарий требует перезапуска, `Workflow` вызывает следующий `Tool`.
8. `Tool` перезапускает тот же `Resource` через `Adapter`.
9. Результат перезапуска фиксируется как новый `Event`.
10. `Workflow` завершает сценарий после проверки итогового состояния.

В этом примере `Workflow` не знает деталей Docker, `Tool` не обращается к Docker напрямую, `Resource` не содержит логики перезапуска, `Adapter` не решает, нужно ли перезапускать контейнер, а `Event` только фиксирует произошедший факт.
